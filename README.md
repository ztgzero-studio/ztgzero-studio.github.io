# ZTG Studio website

Official website of **ZTG Studio**, an independent publisher of game-ready 3D assets for Unity.

- Production: https://ztgzero-studio.github.io/
- Repository: https://github.com/ztgzero-studio/ztgzero-studio.github.io

The site is static: HTML5, CSS3 and vanilla JavaScript, generated by a small Node.js script with no npm dependencies, and hosted on GitHub Pages. It uses no frameworks, no analytics, no cookies and no third-party runtime services.

## Project layout

```text
data/
  site.json              Studio name, URL, support email, store URL, categories
  products.json          Every product: copy, specs, media, availability
  media-manifest.json    Generated: real pixel sizes of every web image
src/
  lib/html.mjs           Escaping template tag (all data is escaped by default)
  components/            Header, footer, product card, status label, breadcrumbs, images
  templates/layout.mjs   Page shell, SEO and social metadata
  pages/                 One module per page; product.mjs renders every product page
public/                  Copied as-is into dist/: CSS, JS, favicon, images
scripts/
  build.mjs              Validates data and generates dist/
  validate-data.mjs      Schema rules for data/*.json
  optimize-images.py     Makes web copies of marketing renders
  serve.mjs              Local preview server for dist/
tests/site.test.mjs      Checks run against the generated dist/
.github/workflows/deploy.yml
```

`dist/` is generated and ignored by Git. GitHub Actions builds it on every push.

## Requirements

- Node.js 20 or later (CI uses Node.js 24)
- Python 3 with Pillow, only to regenerate images (`pip install Pillow`)

## Run locally

```bash
npm run build
```

```bash
npm run serve
```

Then open http://localhost:4173/. The server serves `dist/` at the site root, like GitHub Pages, including `404.html` for unknown paths.

## Build for production

```bash
npm test
```

This builds `dist/` and runs every check: data schema, page generation, titles and descriptions, canonical URLs and sitemap, internal links and anchors, image alt text and dimensions, JavaScript syntax, no internal product IDs in public output, no placeholder contact details, and no purchase links for unreleased products.

The build stops with a list of errors if `data/*.json` is invalid. It prints a warning while no support email is configured.

## Update products

All product content lives in `data/products.json`. Each product generates its own crawlable page at `/assets/<slug>/` and a card in the catalog. You do not copy HTML to add a product.

To add a product:

1. Add renders with the image script (see below) under a new `mediaKey`.
2. Add an entry to `products`. Required fields: `internalId`, `name`, `shortName`, `slug`, `seoTitleSuffix`, `metaDescription`, `mediaKey`, `categories`, `availability`, `availabilityNote`, `storeUrl`, `version`, `summary`, `description`, `highlights`, `features`, `specs`, and `media`. The other Vorthak fields (`rigging`, `animations`, `compatibility`, `contents`, `limitations`, `productionNotes`, `documentation`) are expected by the product page template.
3. Run `npm test`.

Rules the validator enforces:

- `name` is the public name. `internalId` (for example `MON001`) is never shown publicly, and must not appear in the name, slug or any file in `dist/`.
- `availability` is `available`, `coming-soon` or `in-development`. Only `available` products may have a purchase button, and they must have a Unity Asset Store `storeUrl`.
- `categories` must use ids from `site.json`. The catalog filter and home page category counts update automatically.
- Every gallery image needs alt text that names the product.

Only list real products with verified specifications. Leave out anything you have not measured.

## Add new images

Source renders stay in the marketing folder and are never modified. The script writes resized WebP copies (and the social JPEG) to `public/images/products/vorthak/` and records their real sizes in `data/media-manifest.json`:

```bash
python scripts/optimize-images.py "D:/IAS/AssetStore/MON001_Marketing"
```

To add images, edit the `SOURCES` table in `scripts/optimize-images.py`, re-run it, and reference the new key from `products.json`. Public file names use the product name, never the internal ID. Templates read width and height from the manifest, so images never cause layout shifts.

## Maintain Vorthak content

Vorthak's public name is **Vorthak, the Mountain’s Wrath**. Its facts come from the validated package (`MON001_Product_Listing.md` and the Unity/Blender validation reports): 55,718 triangles, a 20-bone Generic rig, three clips (Idle_01, Walk_01, Attack_01), 4096 × 4096 PBR textures, URP/Lit, tested with Unity 6000.6.6f1 and URP 17.6.

When a new package version ships, update `version`, `specs`, `compatibility` and `contents` in `products.json` from the new validation report. When it goes live on the Asset Store, see [Update Unity Asset Store links](#update-unity-asset-store-links).

## Configure customer support

The support email is not set yet. Until it is, the Support page shows a clear "being set up" notice and the build prints a warning. **This blocks a complete Unity Publisher Profile.**

1. Create a support mailbox you will monitor.
2. Set it in `data/site.json`:

   ```json
   "supportEmail": "support@your-real-domain"
   ```

3. Run `npm test` and push. The Support page then shows a `mailto:` link, and the tests check that it is the only email on the site. The validator rejects placeholder addresses such as `example.com`.

## Update Unity Asset Store links

Vorthak is marked **Coming Soon** because its listing is not live yet. When Unity approves it:

1. In `data/products.json`, set `"availability": "available"` and `"storeUrl"` to the live listing URL (it must start with `https://assetstore.unity.com/` or `https://marketplace.unity.com/`).
2. Optionally set `"unityPublisherUrl"` in `data/site.json` to your publisher page. The home page CTA then links to it.
3. Run `npm test` and push.

Never set a store URL before the listing is live.

## GitHub Pages deployment

`.github/workflows/deploy.yml` runs on every push to `main` and on manual dispatch:

1. `actions/checkout`, `actions/setup-node` (Node.js 24), `npm ci`
2. `npm test` (build plus all checks; a failure stops the deployment)
3. `actions/configure-pages`, `actions/upload-pages-artifact` with `dist/`
4. `actions/deploy-pages` in the `github-pages` environment

One-time setup: in the repository, go to **Settings ▸ Pages ▸ Build and deployment** and set **Source** to **GitHub Actions**. Do not also configure branch deployment.

To redeploy without changes, open **Actions ▸ Deploy to GitHub Pages ▸ Run workflow**.

## Troubleshooting

| Problem | Fix |
|---|---|
| Build fails with "Invalid site data" | Read the listed fields; each message names the product and field. |
| A test fails with "broken link" | A template or product entry references a page, image or anchor that does not exist. |
| Images missing locally | Re-run `scripts/optimize-images.py`, then `npm run build`. |
| Deployment job fails with a Pages error | Check that **Settings ▸ Pages ▸ Source** is **GitHub Actions**. |
| Site shows old content | Wait for the workflow to finish, then hard-refresh. GitHub Pages caches files for about 10 minutes. |
| Styles or scripts missing on a deep page | All paths are root-relative (`/css/site.css`). They work at the root of a user site; if the site moves under a sub-path, see below. |

## Custom domain migration

1. Buy the domain and add DNS records for GitHub Pages: `A` records to GitHub's Pages IPs for the apex, or a `CNAME` to `ztgzero-studio.github.io` for a subdomain.
2. In **Settings ▸ Pages**, enter the custom domain and enable **Enforce HTTPS** when it becomes available. With Actions deployment, no `CNAME` file is needed in the repository.
3. Change `"url"` in `data/site.json` to the new origin, ending with `/`. Canonical URLs, Open Graph tags, the sitemap and `robots.txt` all derive from it.
4. Update the Website and Customer Support URL in the Unity Publisher Profile.

The site uses root-relative paths, so it must be served at the root of a domain (a user site or a custom domain), not under a project sub-path.
